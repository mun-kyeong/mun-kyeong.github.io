## 클로드 스킬 모니터링을 생각하게 된 계기

Claude Code 스킬이 늘어나면서 가장 먼저 생긴 문제는 **무엇이 실제로 쓰이고 있는지 알 수 없다는 것**이었습니다.

폴더에는 스킬이 계속 쌓이는데, 제가 자주 쓰는 건 몇 개뿐이었습니다. 그렇다고 제가 안 쓴다는 이유만으로 지우기도 어려웠습니다. 다른 팀원은 자주 쓰고 있을 수 있었기 때문입니다.

반대로 제가 잘 모르는 스킬이 팀에서는 많이 쓰이고 있다면, 어떤 식으로 사용하는지도 알고 싶었습니다. 어떤 옵션을 붙이는지, 어떤 입력 형태를 주로 쓰는지를 알면 제 작업 방식에도 가져올 수 있기 때문입니다.

그래서 Claude Code의 스킬 사용 기록을 Google Sheet에 모으기로 했습니다.

목표는 복잡하지 않았습니다.

* 어떤 스킬이 많이 쓰이는지
* 어떤 스킬이 거의 또는 전혀 쓰이지 않는지
* 사람마다 어떤 스킬을 사용하는지
* 같은 스킬을 어떤 옵션이나 입력 방식으로 사용하는지

결국 스킬을 계속 유지할지, 개선할지, 지울지를 판단할 수 있는 최소한의 데이터를 모으는 게 목적이었습니다.

## 먼저, 스킬은 이미 중앙에서 관리되고 있었다

저희 회사에서는 Claude 스킬을 각 프로젝트에서 따로 관리하지 않고, **스킬만 모아둔 별도의 공용 레포지토리**에서 관리하고 있었습니다.

새로운 스킬이 이 스킬 레포의 `main` 브랜치에 머지되면, GitHub Actions로 구성된 동기화 워크플로우가 각 프론트엔드 개발 레포지토리의 `develop` 브랜치에 해당 스킬을 자동으로 반영합니다.

대략 이런 구조입니다.

![sync-repo](/assets/images/blog/2026-08-24-claude-code-skill-usage-monitoring/sync-repo.png)

각 프론트엔드 레포에는 동기화된 `.claude/skills` 폴더가 생기고, 개발자는 그 안에 있는 스킬을 사용합니다.

이 구조가 이미 있었기 때문에 스킬 사용량을 집계할 때도 별도의 스킬 등록 시스템을 만들 필요는 없었습니다.

공용 스킬 레포가 전체 스킬의 기준이 되고, 각 개발 레포의 `.claude/skills`는 현재 배포된 스킬 목록을 보여 주는 역할을 했습니다.

이 덕분에 단순히 “호출된 스킬”뿐 아니라 “존재하지만 한 번도 호출되지 않은 스킬”까지 함께 볼 수 있었습니다.

## 호출 횟수만 모아서는 부족했다

처음에는 스킬별 호출 횟수만 모으면 될 거라고 생각했습니다.

예를 들어 `/ship`이 한 달 동안 30번 호출됐다면 이런 식입니다.

```text 
2026-08  ship  30
```

그런데 이 방식에는 바로 문제가 있었습니다.

한 번도 사용되지 않은 스킬은 호출 기록 자체가 생기지 않습니다.

예를 들어 현재 배포된 스킬이 다음 세 개라고 해 보겠습니다.

```text 
ship
senior-review
old-skill
```

실제 사용 기록이

```text 
ship           30회
senior-review  12회
```

뿐이라면, 호출 데이터만으로는 `old-skill`이 존재하지만 0회 사용된 건지 알 수 없습니다.

정작 가장 보고 싶었던 삭제 후보가 데이터에서는 아예 보이지 않는 셈입니다.

그래서 **호출 기록과 별개로 현재 배포된 스킬 목록도 같이 수집하기로 했습니다.**

다행히 이 목록을 따로 사람이 관리할 필요는 없었습니다.

훅이 실행될 때 현재 레포의 `.claude/skills` 폴더를 읽어 스킬 이름 목록을 함께 보내도록 했습니다.

이미 공용 스킬 레포에서 각 개발 레포로 스킬이 자동 동기화되고 있었기 때문에, `.claude/skills` 자체가 현재 배포된 스킬 목록 역할을 했습니다.

즉, 호출 기록을 통해 “얼마나 썼는지”를 보고, 스킬 목록을 통해 “존재하지만 안 쓴 스킬이 무엇인지”를 보는 구조로 나눴습니다.

## 무엇을 모을지 먼저 정했다

이 시스템에서 실제로 필요한 데이터는 몇 가지뿐이었습니다.

| 데이터   | 보는 목적                             |
| ----- | --------------------------------- |
| 스킬 이름 | 어떤 스킬이 실제로 사용되는지                  |
| 호출 횟수 | 많이 쓰이는지, 거의 안 쓰이는지                |
| 사용자   | 특정 사람만 쓰는 스킬인지                    |
| 월     | 사용량이 시간에 따라 변하는지                  |
| 호출 방식 | 직접 slash command로 불렀는지, 모델이 호출했는지 |
| 인자 속성 | 어떤 옵션이나 입력 방식으로 사용하는지             |
| 스킬 목록 | 사용량이 0인 스킬이 무엇인지                  |

여기서 단순 호출 횟수 외에 인자까지 보려고 한 이유는 스킬의 사용 방식을 알고 싶었기 때문입니다.

예를 들어 `/ship`이 30번 사용됐는데 그중 25번이 `commit` 모드였다면,

```text
/ship commit
```

매번 `commit`을 입력하게 둘 필요가 있는지 다시 생각해 볼 수 있습니다.

또 `/senior-review`를 사용할 때 파일 하나를 넣는지,

```text
/senior-review src/app/page.tsx
```

Git range를 넣는지,

```text 
/senior-review HEAD~3..HEAD
```

같은 차이도 볼 수 있습니다.

이런 정보는 단순 호출 횟수만으로는 알 수 없습니다.

## 인자의 실제 값은 저장하지 않았다

인자를 수집하더라도 실제 값을 그대로 저장하지는 않기로 했습니다.

처음에는 `/ship --draft`라면 `--draft`를 그대로 보내는 정도만 생각했습니다.

그런데 실제 Claude Code 사용 기록을 보다 보니 커맨드 뒤에 항상 깔끔한 옵션만 붙는 것은 아니었습니다.

예를 들어 이런 입력이 있었습니다.

```text
/ship commit 먼저하고 {"code":401,"body":null,"message":"..."}
```

사용자가 앞선 작업 결과나 API 응답을 그대로 붙여 넣은 경우입니다.

인자 원문을 그대로 전송했다면 이런 내용도 팀 공용 Google Sheet에 들어갈 수 있었습니다.

그래서 실제 값은 버리고 **어떤 형태의 인자가 들어왔는지만 남기기로 했습니다.**

| 실제 입력                             | 저장되는 값                 |
| --------------------------------- | ---------------------- |
| `/ship --draft`                   | `--draft`              |
| `/ship commit`                    | `mode:commit`          |
| `/senior-review src/app/page.tsx` | `arg:path`             |
| `/senior-review HEAD~3..HEAD`     | `arg:range`            |
| `/ship commit 먼저하고 {...}`         | `arg:text,mode:commit` |

플래그는 이름 자체가 스킬에서 미리 정해진 값이라 그대로 남겼습니다.

짧은 소문자 단어가 첫 번째 인자로 오면 서브커맨드로 보고 `mode:` 형태로 기록했습니다.

나머지는 실제 내용 대신 `path`, `range`, `word`, `text` 정도로만 분류했습니다.

덕분에 어떤 파일을 리뷰했는지, 어떤 브랜치를 썼는지 같은 값은 알 수 없습니다. 대신 제가 보고 싶었던 “경로를 넣어서 쓰는지”, “range를 넣어서 쓰는지”, “어떤 모드를 자주 쓰는지” 정도는 남습니다.

수집되는 정보는 줄었지만, 목적에는 충분했습니다.

## 전체 구조는 단순하다

구조는 세 부분으로 나뉩니다.

Claude Code의 Hook이 스킬 사용 시점을 잡고, 셸 스크립트가 필요한 정보만 남겨 Apps Script로 보냅니다. Apps Script는 받은 값을 Google Sheet에 집계합니다.

![mermaid-1](/assets/images/blog/2026-08-24-claude-code-skill-usage-monitoring/mermaid-1.png)

스킬 호출은 두 경로에서 잡았습니다.

사용자가 `/ship`처럼 직접 slash command를 입력하는 경우에는 `UserPromptSubmit`이 발화하고, 사용자가 직접 스킬 이름을 입력하지 않았더라도 Claude가 알아서 Skill tool을 호출하면 `PostToolUse`가 발화합니다.

같은 한 번의 사용이 두 경로에서 모두 잡힐 수도 있기 때문에, 서버에서는 같은 세션에서 같은 스킬이 20초 안에 들어오면 하나로 합치도록 했습니다.

정확한 이벤트 추적보다는 사용량 집계가 목적이었기 때문에 이 정도 기준이면 충분했습니다.

## 아무 Claude 사용이나 기록하지는 않는다

`UserPromptSubmit`은 일반적인 대화를 입력할 때도 실행됩니다.

예를 들어

```text
이 코드 왜 안 돼?
```

같은 입력도 Hook을 통과합니다.

하지만 필요한 건 스킬 사용 기록뿐이라, 가장 먼저 slash command 형태인지 확인합니다.

slash command가 아니면 바로 종료합니다.

slash command라고 해도 모두 기록하지는 않습니다. 현재 레포의 `.claude/skills` 폴더에 있는 이름인지 다시 확인합니다.

그래서 `/clear`, `/model` 같은 Claude Code 내장 커맨드나 외부 플러그인 커맨드는 빠집니다.

최종적으로 집계되는 것은 각 레포에 동기화된 공용 스킬뿐입니다.

개인 프로젝트처럼 `.claude/skills`가 없는 곳에서는 아무것도 기록되지 않습니다.

## 시트는 세 가지 관점으로 나눴다

데이터를 모은 뒤에는 크게 세 종류의 탭으로 나눴습니다.

### 개인 탭

팀원마다 하나씩 있고, 각 스킬의 월별 사용량과 사용 방식을 기록합니다.

```text 
month    skill          params        count
2026-08  ship           (전체)          30
2026-08  ship           mode:commit     25
2026-08  ship           --draft          6
2026-08  senior-review  (전체)          12
2026-08  senior-review  arg:path         4
```

여기서 `(전체)`가 실제 호출 횟수입니다.

그 아래의 `mode:commit`, `--draft`, `arg:path`는 그 스킬을 어떤 방식으로 사용했는지를 보여 줍니다.

속성 행의 합계와 `(전체)`은 일치하지 않을 수 있습니다.

한 번의 호출에 여러 속성이 동시에 들어갈 수 있기 때문입니다.

예를 들어 한 번의 사용에서

```text
arg:text, mode:commit
```

이 같이 기록될 수 있습니다.

반대로 아무 인자 없이 호출하면 `(전체)`만 증가합니다.

그래서 실제 호출 수를 볼 때는 항상 `(전체)` 행을 기준으로 봅니다.

### 스킬목록 탭

호출 기록만으로는 사용량이 0인 스킬을 볼 수 없기 때문에, 별도의 `스킬목록` 탭도 두었습니다.

```text
skill          최초 확인   최근 확인   상태
ship           2026-08    2026-09    활성
senior-review  2026-08    2026-09    활성
old-skill      2026-07    2026-08    2026-08 이후 없음
```

이 목록은 사람이 직접 관리하지 않습니다.

각 개발 레포로 공용 스킬이 자동 동기화되고 있기 때문에, 훅이 실행될 때 `.claude/skills` 폴더를 읽어 현재 배포된 스킬 목록을 함께 보냅니다.

이 정보를 누적하면 어떤 스킬이 현재 팀에 배포되어 있는지 확인할 수 있습니다.

여기서 중요한 건 **사용 여부와 존재 여부를 따로 본다는 점**입니다.

예를 들어 `ship`이 이번 달에 한 번도 호출되지 않았더라도 `.claude/skills`에는 계속 존재한다면, “현재 배포되어 있지만 사용량이 0인 스킬”입니다.

반대로 공용 스킬 레포에서 제거되어 이후 동기화 대상에서도 빠진 스킬이라면, 과거 사용 기록은 그대로 남겨 두고 마지막으로 확인된 시점만 기록합니다.

이렇게 해 두면 이미 삭제된 스킬과 아직 존재하지만 아무도 쓰지 않는 스킬을 구분할 수 있습니다.

### 종합 탭

개인별 탭을 모두 합친 팀 전체 사용량입니다.

```text
month    skill          params        total
2026-09  ship           (전체)          42
2026-09  ship           mode:commit     30
2026-09  old-unused     (전체)           0
```

![excel-img](/assets/images/blog/2026-08-24-claude-code-skill-usage-monitoring/excel-img.png)

최근 3개월에 대해서는 스킬 목록에는 있지만 사용 기록이 없는 경우 `(전체) 0`을 채웁니다.

이 값으로 최근 몇 달 동안 사용되지 않은 스킬을 바로 볼 수 있습니다.

## 실제로 확인할 수 있었던 것

데이터를 모으고 나니 처음 궁금했던 질문들은 대부분 바로 확인할 수 있었습니다.

먼저 어떤 스킬이 많이 쓰이는지 볼 수 있습니다.

`params = (전체)`만 필터해서 호출 횟수 순으로 정렬하면 팀에서 실제로 자주 쓰는 스킬이 나옵니다.

반대로 최근 몇 달 동안 계속 0인 스킬도 바로 확인할 수 있습니다.

예전에는 “이거 아무도 안 쓰는 것 같은데” 정도였다면, 이제는 실제 사용 기록을 보고 삭제 여부를 판단할 수 있습니다.

사람별 차이도 볼 수 있습니다.

특정 스킬을 한 명만 계속 쓰고 있다면 공용 스킬로 유지할 필요가 있는지 다시 볼 수 있습니다.

여러 사람이 한 번씩 써 봤지만 이후 다시 쓰지 않는 스킬도 확인할 수 있습니다. 이런 경우에는 스킬 자체가 불편한지, 용도가 애매한지 살펴볼 수 있습니다.

옵션 사용 패턴도 볼 수 있습니다.

예를 들어 `ship`이 30번 사용됐고 그중 25번이 `mode:commit`이라면 `commit`을 기본 동작으로 바꾸는 걸 검토할 수 있습니다.

반대로 스킬 문서에는 여러 옵션이 있는데 실제 사용 기록에 한 번도 나타나지 않는 옵션이 있다면, 그 옵션을 계속 유지해야 하는지도 다시 생각해 볼 수 있습니다.

스킬 사용량을 보려고 만든 시스템이지만, 실제로는 스킬 인터페이스를 정리하는 데에도 꽤 유용했습니다.

## 셋업은 최소한으로 두었다

각 개발자가 직접 설정해야 하는 값은 두 개뿐입니다.

`~/.claude/settings.json`에 토큰과 Apps Script endpoint를 넣습니다.

```json id="lg3y87"
{
  "env": {
    "SKILL_USAGE_TOKEN": "<팀 공유 시크릿>",
    "SKILL_USAGE_ENDPOINT": "https://script.google.com/…/exec"
  }
}
```

이 값이 없으면 로깅 스크립트는 아무것도 하지 않습니다.

Hook 설정과 실제 로깅 스크립트는 공용 스킬 레포에서 함께 관리하고, 기존에 사용하던 GitHub Actions 동기화 워크플로우를 통해 각 프론트엔드 개발 레포로 배포합니다.

즉, 스킬뿐 아니라 로깅에 필요한 스크립트와 프로젝트 설정도 같은 흐름으로 배포됩니다.

각 개발자는 로컬 환경에 인증에 필요한 값만 넣으면 됩니다.

공용 로깅 방식이 바뀌더라도 각 사용자가 직접 훅 설정을 다시 수정할 필요는 없습니다.

## 결국 필요했던 건 사용량 숫자보다 판단 근거였다

이걸 만든 이유는 단순히 인기 있는 스킬 순위를 보고 싶어서가 아니었습니다.

스킬을 계속 유지할지, 고칠지, 지울지 판단할 근거가 필요했습니다.

예전에는 오래된 스킬을 보면서도 혹시 누군가 쓰고 있을까 싶어 쉽게 지우지 못했습니다.

지금은 최근 몇 달 동안 실제 호출이 없었다는 걸 확인한 뒤 삭제를 이야기할 수 있습니다.

반대로 제가 잘 몰랐던 스킬이 팀 전체에서 많이 쓰이고 있다면, 어떤 방식으로 사용하는지까지 보고 제 작업에도 가져올 수 있습니다.

많이 쓰이는 옵션은 기본값 후보가 되고, 아무도 쓰지 않는 옵션은 정리 후보가 됩니다. 특정 사람만 사용하는 스킬은 정말 공용으로 유지해야 하는지도 다시 볼 수 있습니다.

처음부터 복잡한 분석 시스템을 만들 생각은 없었습니다.

프롬프트나 코드는 모으지 않고, 스킬 이름과 사용 방식 정도만 기록해서 Google Sheet에서 볼 수 있으면 충분했습니다.

결과적으로 그 정도 데이터만으로도 “이 스킬을 계속 유지해야 하나?”라는 질문에는 이전보다 훨씬 쉽게 답할 수 있게 됐습니다.
